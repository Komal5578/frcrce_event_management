# Audit and fix plan: security, integrity, scale, UX (2026-10-25)

Scope: `/worker` (API + D1), `/frontend` (Next.js), deployment config, git history.
Method: full read of the Worker and the main screens; attack probes and a 1,000-user simulation against an
**isolated local copy** (local D1, never the deployed Worker); the existing Playwright suite; Lighthouse; a
pattern scan of git history. Re-runnable scripts are in `worker/audit/` (see "How to re-run").

Evidence labels: **verified** = reproduced by a script or in the browser. **code-read** = seen in source, not
executed. **inferred** = follows from repo facts, not tested.

## 0. What I did not test (read before trusting the numbers)

- Nothing was sent to the deployed Worker, remote D1 or Vercel. Load numbers are from local SQLite with no
  network latency: they are an **upper bound**, good for comparing before and after, not for capacity promises.
- Production CPU limits (Workers plan), D1 `rows_read` billing and Vercel Firewall settings are unknown.
  The local D1 did not report `rows_read`; the figure in P2 is a hand estimate.
- WCAG was checked with Lighthouse and the existing Playwright structure tests only. No manual screen-reader pass.
- The secret scan is a pattern scan of 16 commits, not an exhaustive tool run.

## 2. Security findings

| ID | Sev | Status | Finding | Fix |
|---|---|---|---|---|
| S1 | High | inferred | The same known password (`demo-password-2026`) is committed in `worker/seed.sql`, `worker/smoke.mjs` and `frontend/e2e/auth.ts` for the admin, coordinator and student accounts. CLAUDE.md says remote D1 was reseeded from that file, so those accounts probably exist in production. Anyone who reads the repo can sign in as admin. **Check with one login attempt yourself before acting.** | Remove demo accounts from prod D1. Keep seed data for dev/staging only. Tests read the password from an env var. If a public demo is wanted, deploy a second Worker+D1 with `DEMO_LOGIN=true` and no real data. |
| S2 | High | verified | Account lockout can be abused: 5 wrong guesses lock the real owner for 15 min, and attempts made while locked are still recorded, so the lock never expires while the attacker keeps trying. The admin account is lockable by anyone who knows its email. | Limit on (IP+email) and on IP; do not record attempts while locked; use a growing delay instead of a hard lock; Cloudflare Rate Limiting binding; Turnstile after 3 failures. |
| S3 | Med-High | verified | Password spray is not throttled: 300 accounts x 1 guess all returned 401, no 429. The Worker is also reachable directly at `*.workers.dev`, so any Vercel-side protection can be bypassed. | Per-IP limit inside the Worker (read `x-forwarded-for` from the Vercel rewrite; `cf-connecting-ip` when direct). |
| S4 | Med | verified | `login_attempts` grows forever for unknown emails (500 junk logins = 500 permanent rows). `sessions` is swept with `DELETE ... WHERE expires_at < ?` on every login, and the plan is `SCAN sessions`. | Cron Trigger purge; index `sessions(expires_at)`; store a hash of the email. |
| S5 | Med | verified | No CSRF defence beyond `SameSite=Lax`. A cross-site `Origin` with `text/plain` was processed by the Worker (409 ALREADY_REGISTERED, meaning it ran). | Require `application/json` and check `Origin`/`Sec-Fetch-Site` on all non-GET requests. |
| S6 | Med | verified | Frontend sends no CSP, `X-Frame-Options`/`frame-ancestors`, `X-Content-Type-Options`, `Referrer-Policy` or `Permissions-Policy`; `X-Powered-By: Next.js` is exposed. API JSON has no `Cache-Control: no-store`. | `headers()` in `next.config.ts`; `poweredByHeader: false`; add headers in the Worker `json()` helper. |
| S7 | Med | verified | No size limits: a 2 MB description was accepted; `notify` body is unbounded and is copied once per registrant (N x size). No request-body cap. | Cap body (64 KB), add `max` to the existing `str()` helper, cap `notify` body at 500 chars. |
| S8 | Med | verified | Wrong types cause 500: `venue_id: {}` and `description: {}` return 500 INTERNAL; `title: 12345` and `type: []` are silently accepted. | Same boundary helpers: reject non-strings and non-integers with 422. |
| S9 | Low-Med | verified | A task can be assigned to any user id (an admin was accepted); `notify` accepts any `kind`, so a coordinator can forge `alert`-type notifications. | Assignee must be a student; whitelist `kind`. |
| S10 | Info | code-read | PBKDF2 is 100k iterations (the Workers maximum), below the OWASP guideline. No password change, no reset, sessions never rotate or revoke. | Accept the cap, rely on S2/S3 limits, add change-password and "sign out everywhere" (see U2). |
| S11 | Info | code-read | `frontend/.env.local` holds a Vercel OIDC token. It is untracked (gitignored), so not a leak. | Nothing to do; rotate if the machine is shared. |

What held: cookie is `HttpOnly; Secure; SameSite=Lax`; only the SHA-256 of the token is stored; token is dead
after logout; every query is parameterised (login SQL injection returned 401); CSV export neutralises
`=`/`+`/`-`/`@`; React escapes all event text and the only `dangerouslySetInnerHTML` is a static boot script.

## 3. Business-rule and integrity bugs (all verified by `probes.mjs` unless marked code-read)

| ID | Finding | Fix |
|---|---|---|
| B1 | A 5,000-person event was approved in a 30-seat room. UI only greys out small venues. | Check `capacity <= venue.capacity` in `mergePatch`, `updateEvent`, and a trigger for held events. |
| B2 | A past-dated event can be created, approved, opened and registered for. | Require `starts_at > now` on submit and approve; close registration at start. |
| B3 | Nothing moves events through their life: no scheduler exists, so events stay "open" after they start, "ongoing" events are listed under "Events you can join", and reminders never happen (see U3). (code-read plus browser) | Cron Trigger every 10 min: open to ongoing at start, ongoing to completed at end, 24 h reminders, purge (S4). |
| B4 | A student can cancel a registration on a **completed** event; this also promotes a waitlister into a finished event with a notification. | Cancel allowed only while the event is open and before start. |
| B5 | A coordinator can move an **open/approved** event to another venue, date or capacity with no admin re-approval (the clash trigger still protects the venue). | Material changes to approved/open events go back to `pending`, or require admin confirmation. |
| B6 | Admin can cut resource stock 10 to 5 while two overlapping events hold 5+5, and can cut a venue to 5 seats under a 400-seat event. The check uses the largest single allocation, not the overlapping sum. | Guard triggers on `resources` and `venues` updates using the same overlap sum as `alloc_guard_*`. |
| B7 | Waitlist queue-jump: capacity raised 1 to 2, waitlisted user B stays queued and late user C is confirmed. | Trigger on capacity increase promotes the oldest waitlisted first; `register` waitlists if a queue exists. |
| B8 | When 20 requests fight for one slot, the 19 losers are told `RESOURCE_SHORT` ("not enough of that resource") instead of `VENUE_CLASH`, because the resource trigger fires first. The admin is told the wrong reason. | Merge the guards into one trigger with clash first, or check clash in the app before the update. |
| B9 | `updateEvent` checks "capacity >= confirmed" then updates in a separate statement (code-read race). | Trigger on `events.capacity` decrease. |
| B10 | Waitlist order uses `created_at` (ms) then random UUID; under a burst, ties are arbitrary (code-read; positions were dense in the test). | Add a monotonic `seq` column and order by it. |
| B11 | Report "Capacity" column is the **venue** capacity, not the event capacity (code-read, `buildReport`). | Use `e.capacity`; show venue seats separately if wanted. |
| B12 | Reports date filter compares UTC dates; an IST evening/early-morning event can land on the wrong day (code-read). | Filter by campus timezone or send full ISO bounds. |
| B13 | Coordinator calendar says "See what is booked before you pick a slot" but `/api/events` returns only the coordinator's own events (code-read). | Feed it from a venue-bookings endpoint (title hidden, venue and time only). |

## 4. Scalability (local numbers, `load.mjs` and `grow.mjs`)

| ID | Finding | Evidence | Fix |
|---|---|---|---|
| P1 | Login is CPU heavy | 1,000 simultaneous logins took 10.5 s wall (p50 10.3 s) on one local isolate; one idle login is 13 ms. Production spreads across isolates, but check CPU ms per login against your Workers plan limit. | Measure with Workers observability. Keep sessions at 7 days; add Turnstile/queue only if the plan limit is hit. |
| P2 | Lists return everything | After 3,000 events / 60k registrations: student `/api/events` = **2.2 MB**, 39 req/s at c=20 (about 800 on a small DB). `/api/notifications` for 30k rows = 7.4 MB. Reports = 585 KB. Estimated ~85k D1 rows read per student call (hand estimate; on D1 Free's 5M rows/day that is roughly 60 page opens a day). | Server-side filter and pagination (`from=now`, `status`, `limit`+cursor). Keep `confirmed`/`waitlisted` counters on `events`, maintained by the existing triggers, to remove the correlated `COUNT(*)`. Notifications: limit 20 + cursor, index `(user_id, created_at DESC)`, partial index for unread. |
| P3 | Fan-out calls | Resource step makes one request per resource per change; "Mark all read" sends one POST per notification. | Use the existing `/api/resources?from&to` (already returns `in_use`); add `POST /api/notifications/read-all`. |
| P4 | Session and sweep | Every request does a session lookup; login sweep is a table scan (`SCAN sessions`). | Index or Cron purge; consider D1 read replication. |
| P5 | Admin alerts and bookings | `computeAlerts` loads all events, tasks, bookings and conflicts in JS; `listBookings` is O(n squared). 45 req/s on aged data. | Compute in SQL for a bounded window. |
| P6 | Polling | `unread-count` every 30 s per open tab: 1,000 users is about 33 req/s; it handled 337 to 900 req/s locally, so safe today. | Keep; pause when hidden (SWR default). Revisit only if P2 is not fixed. |

Held under load: no overbooking (1,000 vs 100 seats), exact waitlist positions (1..850 dense after 50 cancels),
exactly one approval for 20 rivals, 6,000 page-load calls from 1,000 users with 0 errors (p95 2.9 s on one
local core).

## How to re-run

All scripts target `http://localhost:8787` (override with `BASE=`). Never point them at production.
```
cd worker
npx wrangler d1 migrations apply college-events-v2 --local --persist-to /tmp/audit-state
npx wrangler d1 execute college-events-v2 --local --persist-to /tmp/audit-state --file seed.sql
node audit/genseed.mjs > /tmp/loadseed.sql   # 1,000 students + 30 coordinators
```
`genseed.mjs` prints one INSERT per row (a single multi-row INSERT is rejected by D1 as too long). Then:
```
npx wrangler d1 execute college-events-v2 --local --persist-to /tmp/audit-state --file /tmp/loadseed.sql
npx wrangler dev --local --port 8787 --persist-to /tmp/audit-state &
node audit/probes.mjs          # attack and rule probes; prints HOLDS/BROKEN/NOTE
node audit/load.mjs browse race approve sat
# aged-data run: execute audit/grow.sql the same way, then node audit/grow.mjs
```
Probes mutate data (they cut a venue's capacity, for example): rebuild the local DB between runs.
